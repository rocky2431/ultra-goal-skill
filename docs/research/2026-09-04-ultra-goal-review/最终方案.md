## 0 · 架构

> **主模型持有目标与反馈,脚本记录可核对事实,hook 补漏,宿主提供执行与续跑。**

我原来的说法是"门就是循环,所以不需要宿主的目标模式"。**这句被一个读数推翻:** Kimi 第一轮跑了约 56 分钟、原生 trace 记录 134 次工具调用、**一次 `CreateGoal` 都没有**。普通宿主回合本身就能长时间执行多步任务;没保证的只是"结束后自动开下一轮"和"进程死后复活"。

Stop 只承担一个很窄的职责:**识别所属 run,检查明确约定的收尾遗漏,决定是否值得一次纠正。** 它不是调度器,不是全过程验证,不是无限续跑。

## 1 · 五个已证实的缺陷(阶段 0 的全部内容)

前四条我在综合稿里列了;第五条是 Codex 终审时**新跑一个配对探针**钉死的,把它从"可能"升级成"当前版本的实证缺陷"。

### 1.1 CC 上 allow 附带 `additionalContext` 会续跑

探针 `clean-claude-allow-context`(干净 settings、隔离目录、2.1.260):hook 只发 `hookSpecificOutput.additionalContext` 不带 `decision`,`hook_events` 出现 index 1 与 2,`visible_responses: ["PROBE_CORRECTED"]` —— **回合没结束,模型还照注入内容动了。**

`goal_stop._allow(reason, context)` 有五条路径挂 `additionalContext`(ceiling 到、unknown、green、空转、预算用尽)。它们在主力宿主上不是"结束并告知",**是一边说停下一边不让停。**

**修法:放行不附带任何模型上下文。**

而**义务往哪去,这里有一条我原来写错的**:我曾把它分给"阻塞时的 reason + 下一次可注入事件"。Codex 指出后者不是保证通道 —— Kimi 的 task / system-triggered turn 不触发 `UserPromptSubmit`,`SessionStart` 也不是每次续跑或下一 turn 的保证事件。

**正确答案:重要结果必须在 Stop 之前就由普通工具流可见,并在放行前写入耐久状态。下一事件注入只能是 best effort,不能承担 correctness。**

这不是一个缺口,这就是结论:**义务从 hook 搬回运行自己的循环(skill 的指令),那本来就是它该在的地方** —— 正好是第 0 节那句架构。

### 1.2 `python3 X || python X` 启动器吞掉 exit 2

我 v2.7.0 为 Windows 兼容写的。我自己复现:

```
$ echo '{"x":1}' | python3 probe.py                       → RAN stdin=8, exit=2
$ echo '{"x":1}' | sh -c 'python3 probe.py || python probe.py'
  RAN stdin=8      ← 第一次,故意 exit 2
  RAN stdin=0      ← 第二次,stdin 已被吃光
  最终 exit=0      ← exit 2 被吞
```

当时的理由是"后半只在命令找不到时触发,因为这些 hook 真跑起来一律退出 0"。**exit 2 恰好就是四家文档里"有意纠正"的机制,而这个理由十秒钟可测。**

**修法:先选解释器,再只执行一次,保留退出码。**

### 1.3 exit 2 的保护必须覆盖启动路径

实测:**Python 文件不存在、argparse 参数错误,都返回 2**,而四家都把 2 当"有意阻塞"。我们的 fail-open 全活在 `run_hook` 的 `try/except` 里 —— 进不到那里的失败会被读成一次阻塞。

### 1.4 `.goals/active` 没有会话归属

只按 cwd + slug。**同一个 cwd 里另一个任务的 Stop 也会触发我们的检查。** 三轮审查没人提过。

**修法:记录会话 ID,Stop 只认领匹配的 run。** 限定照抄:**session ID 是归属信息,不是防伪密钥。**

### 1.5 我们确切的 `_deny` 载荷在 Codex 上让阻塞整个失效

Codex 终审新做的配对探针,本机 `codex-cli 0.150.1`、隔离目录、同一注册方式:

```
实验组  逐字段复制候选 _deny(reason, context) 的非空 context 形状:
        顶层 decision:block / reason
        + hookSpecificOutput.{hookEventName, permissionDecision:deny,
                              permissionDecisionReason, additionalContext}
   → 1 次 Stop 回调,只有 PROBE_INITIAL,没有续跑

正控    只发顶层 decision:block / reason
   → 2 次 Stop 回调(第二次 stop_hook_active:true)
     PROBE_INITIAL 之后又输出 PROBE_CORRECTED
```

正控排除了"hook 没加载"这个替代解释。**结论:混合载荷使本应有效的顶层 block 一并失效。**

我第 1 轮把"两个权威源都发"记成优点(说它"在一个和两个权威源都无关的宿主上回本了")。**在 Codex 上它是让阻塞整个失效。** 准确的表述是"对 Stop 这个事件不受支持的混合 schema",不是"Codex 拒绝 `hookSpecificOutput`"—— 那个字段在其他事件有合法用途,错要钉在 event-specific schema 上。

**修法:删掉 Codex 不支持的 nested Stop 字段;修后必须再跑同级正控,不能把本轮失败外推为所有版本。**

## 2 · 一条我读错的量

我从 2.1.260 二进制读出 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP ?? 8`,据此设了"每家预算 = 上限 − 1"。Codex 指出那是"**连续无工具进展**的续跑保护"。我回去核了:

```
stopHookBlockingCount: 0      ← 在状态转移里被重置
blockingErrors.length > 0 → qd = go + 1;  if (qd > Vd) 强制结束
```

`go` 就是 `stopHookBlockingCount`。**它数的是"距上一次进展以来的连续阻塞",不是"每回合的阻塞数"。我读对了数字,读错了那个量。**

而 Codex 终审又推进一层,这一层我原稿是错的:

- **"按回合身份划界所以安全"对 zCode 是假话。** `goal_hooks.py:109-125` 自己写着 zCode 既没有语义可用的 chain flag 也没有 turn boundary;上一条链在 interrupt / error / session end 后会把尾巴带进下一 turn。**那是保守的 liveness 损失,不是 turn-scoped 机制。**
- **不能"阶段 0 原样保留、阶段 1 再换生命周期"。** 一旦第 3 节改成"只在 completion candidate 跑 anchor",`anchor_checked` 累加的 streak **所测的对象已经变了**。

**修法:保留一个 gate 自有的上界(无限纠正有历史失败,这条有依据),但在新完成协议确定之后把它重定义为"有界的 completion attempts",并明确 zCode 的降级。不再称它为 host cap − 1,也不再声称四家都按回合精确计数。**

## 3 · Anchor 放在哪

我综合稿里的分层方向可取,**但文字开了一个新的自述缺口,而且我误表述了 Codex 的主张。**

**先更正归因:Codex 从没主张"每次业务迭代都跑完整 anchor"。** 它的原意是:验证发生在普通工作流里,按本次改动和验收项选择适用测试 / 真实路径;相关产物验证后又变了,完成前才按影响复验。我把它升级成"每轮跑 anchor",**只是把 Stop 的固定成本搬进了业务循环。**

**再修缺口。** 我同时写了两件互斥的事:"门跑一次" 和 "run 把退出码写成事件、门比对"。后者是同一个执行方**同时作者化 claim 和所谓 evidence** —— 匹配只证明两段自述互相对应。

### 采用的完成契约(Codex 终审版)

1. **run 发出显式 completion candidate。** 它可以是自述,因为只触发检查、不授予通过。**普通 Stop 只表示想结束一个宿主 turn,不等于目标完成。**
2. **门先核** session / run 归属、当前获授权的 spec baseline、当前 anchor identity。任一不匹配都不拿旧结果顶替。
3. **所有必要 worker 已 join**、没有仍会改相关产物的写者。
4. **门对当前状态亲自执行当前 anchor 一次**,只用本次 hook 写下的结果作机械裁决。
5. **hook 自己写 measurement**:run/session identity、spec digest、anchor digest、相关产物或 post-anchor state identity、exit code、output digest。**整树 hash 只是保守近似,不能让无关文件变化冒充相关性。**
6. **本次检查后相关状态再变,completion candidate 失效。** green 只证明这个 anchor 在这份状态上 exit 0;是否满足语义验收仍由模型 / owner 按需求证据判断。

**门不读取历史 green 来放行** —— 旧行根本不是 pass 输入,只作审计。于是"run 上次执行后到完成声明之间变了什么"这个 stale-row 问题不存在。

**非 completion 的 Stop:最多做短的、确定性的遗漏提示。只看证据存在不能阻塞也不能放行完成 —— 存在、mtime、hash、勾选框都不是完成 oracle。**

而运行侧的正确措辞是:**在相关变更后、需要反馈或准备完成时,用普通工具执行适用验证。** 不是每轮固定跑全套。

## 4 · 解冻:授权、观察、生命周期是三件事

**"冻结 owner 的条件,不冻结整份工作认识"这个方向成立。** 依据是原生目标模式的实现:不可变的是那一句条件(在会话状态里,模型碰不到),文档完全可变,提示词只是指着它。所以 Protoss 的 `GOAL.md` 被改 38 次没有违反任何东西。我们把两者混成一件 —— 把条件写进了文档,于是只能去冻结文档。

**但我原稿两处错:**

### 4.1 "留痕即可"会让未授权改约洗成新基线

我写的是"一条轨迹 + 一个裁定 ID 就建立新基线"。**任何能写文件的 run 也能同时写这两样。** ID 是关联信息,不是授权凭据 —— 和 session ID 不是防伪密钥同理。

**re-baseline 至少要记录:变更 diff、旧/新 baseline、裁定来源,并先满足其一 —— owner 在当前受信通道明确批准,或旧约已明确授权该类变更。** agent 可以提 challenge,**不能自己把 material goal change 裁成 owner change。**

### 4.2 "删除形状,代码不动"是事实错误

`goal_stop.py:543-558` 永远拿**第一条** `anchor_checked.spec_digest` 当基线,没有识别新 baseline 的路径。所以二选一,不能同时写:

- **要么**改代码:一个被 gate 消费的 re-baseline 状态转移 + 回归测试;
- **要么**不改代码:结束旧 run,由 owner 以新 spec 开一个新 run。

### 4.3 `impossible` 不进 anchor 的颜色轴

green / red / unknown 是**本次命令的观察**:通过、失败、无法测量。`impossible` 是**对未来可达性的语义判断**,属于 run disposition。一次 exit 1 不能证明永久不可达,一次 timeout 也不能。

**两条正交轴:**

| 轴 | 取值 |
|---|---|
| Anchor observation | `green` / `red` / `unknown` |
| Run disposition | `in_progress` / `input_required` / `blocked_retryable` / `budget_exhausted` / `unachievable` / `completed` / `canceled` |

缺凭据是 `input_required`,服务故障是 `blocked_retryable`,预算用尽是 `budget_exhausted`,anchor exit 1 只是 `red`。**只有目标在当前冻结约束 / 授权 / 环境下确实自相矛盾或永久失去实现路径,并经独立证据确认,才是 `unachievable`。主模型说"不可能"只能触发核查,不能成为证明。**

这套词汇作为**报告用语**保留;**现在没有证据要求给 gate 加一个代码 outcome。** 只有当 `unachievable` 有真实消费者(停止后续重试、产生明确的未完成终态,且该宿主确实能执行这个终止)才实现它。

## 5 · 四件"进化机制":暂不加入,4/4 未过门槛

我从 Protoss 提了四件(轨迹文件、裁定 ID/覆盖、撤回台账、校验承诺)。按我自己设的门槛"每件对应一次复现过的失败",**Codex 判定 4/4 未过,而且论证是取证,不是意见。我接受全部四条。**

- **轨迹文件。** 我引的数字来自一个**未钉版本的移动快照**:391 commits / 354 个 `loop:` 对应 `17e8deb`,而那个 revision 的 TRAJECTORY 是 **6,663 行**;6,702 行出现在下一个 commit(392);它读 live repo 时已 **459 commits**。**我那个数字组合不是可重放的同一时点读数。** 更关键:`TRAJECTORY.md:6306-6309` 自己写着同一教训**在 TRAJECTORY 里出现过六次**,而每轮真读的 `JUDGE.md` 命中 0。**那是"日志没有消费者"的失败 —— TRAJECTORY 已存在且没防住它。**
- **裁定 ID。** `Who` 列早就区分 `owner|agent`。而我给的直接理由是错的:`Delete anything no longer true` 位于 `## Carry-over` 内,**只约束 State/Lessons/Next,不作用于 `decisions.md`** —— 我为一条不存在的跨文件删除路径提了个编号体系。
- **撤回台账。** "六条撤回无处可记"在文档自身就不成立:第 7 节就是完整的表。撤回对**这轮审查**有价值,那就留在审查产物里。
- **校验承诺。** 它是轨迹的从属校验,不该另算一件。而照抄 Protoss 的算法会把不完整轨迹判绿:checker 找不到 SHA 时只取标题前 30 字符 `grep -F`,在那个 revision 上**已有三组真实碰撞**(3/2/2),包括三个都以 `loop: pay the pre-registration` 开头的提交。而且"append-only 永不改已有条目"与"下一阶段回填 SHA"二选一。**最关键:`方案与论证.md:61,84,146` 已撤回"每轮强制 commit、未授权不自动提交",我的 §5.4 和阶段 3 又把它带回来了 —— 和已采纳的架构直接冲突。**
- **"scope 完全不相交是唯一并行写条件"** 被我引的同一份 `LEDGER.md:2174-2176` 打穿:三次连续事故,path scope 不相交仍通过**共享 Git index** 互相裹入,最终修复是独立 worktree;反过来有 worktree / 事务 / 明确 merge owner 时 scope 可以重叠。**正确规则:并行写需要互斥所有权、真实隔离或冲突控制;共享可变依赖则串行。**

### 5.1 唯一保留下来的东西,是一句判据而不是机制

**一份没有消费者的记录不是修复。** 这句话从 Protoss 那条六次教训里长出来,而它同时否掉了我提的四件里的三件。它该进 `anti-patterns.md`,不该变成任何人的默认文件。

**一处补正(不推翻 Codex 的裁决,只是把它说全):** TRAJECTORY 虽然没防住那次失败,却是**让"六次"变得可数的那个仪器** —— 检测器不是修复,但也不是无用。真正的修复是把规则晋升进被消费的文档。这一点强化了它的结论而不是削弱:**要加的是"会被恢复流程实际读取的 material 记录",不是每 tick 一条五字段日记。**

## 6 · 停做的

- 每次 Stop 跑完整 anchor(第 3 节已解决成本问题)
- **把"两次相同签名即放行"当硬规则** —— 相同失败输出或文件树没变化不能证明没有进展,**两次失败便退出会误伤调查和长期修复**。改成记录 + 提示,不自动释放
- 把 `FROZEN_SECTIONS` 做成制品声明 —— 能改的是 `ceiling:`、`budget:` 这类阈值,**不能改的是"哪些东西算冻结"**
- 读未文档化的字段 —— Kimi 传 `stopHookActive` 而它按构造恒为 false,不携带信息
- 为省 anchor 时间加"工作树有没有变"的判断
- 四件进化机制(第 5 节)
- **宣称四宿主支持**(第 8 节)

## 7 · 执行顺序(采纳 Codex 终审版)

它修掉了我原表的一个依赖倒置:**先定完成生命周期,才知道 streak、event schema 和 re-baseline 该挂在哪** —— 不能先保留旧计数,再在下一阶段把它所计的事件改掉。

| 阶段 | 只做什么 | 通过条件 |
|---|---|---|
| **0** | 修五个已证实缺陷:CC allow-context、解释器 fallback、启动前 exit 2、session ownership、Codex mixed `_deny` | 每个有针对性回归;CC 与 Codex 各有修后正向真探针;同 cwd 双 session 隔离实测 |
| **1** | 定义 completion candidate;门只在该时刻对当前状态亲跑一次当前 anchor 并当场裁决 | 旧 row、错 session/spec/anchor、检查后再写入,都不能放行;一次真实完成路径通过 |
| **2** | 选 re-baseline 语义(owner 授权后同 run 状态转移 / 关旧 run 开新 run);把 anchor observation 与 run disposition 分轴 | 未授权改约不能建立 baseline;旧观察保留;暂不新增 `impossible` gate outcome |
| **3** | 暂不加四件进化机制 | 以后只在"一个具体失败 + 它的消费者"同时出现时,加最小的一项 |
| **4** | 按宿主做完整生命周期验收,分别标注支持状态 | 只对实际通过的宿主作支持声明;共享"四宿主"声明需四家都通过 |

**阶段 0 之前不合并 `host-adaptation`。**

### 每家的验收清单

1. 激活后确实收到 hook
2. 故意漏一次必要步骤,能够纠正
3. **真正放行能够结束**(CC 上今天是失败的,见 1.1)
4. 错误 / 超时不记成功
5. **同 cwd 的另一个 session 保持无影响**(今天做不到,见 1.4)
6. 取消与压缩 / 恢复遵守真实生命周期
7. 必要 worker 结果收齐后才形成结论
8. 原生 goal 已停而 Ultra 证据不足时如实报告

**当前实机覆盖:CC 与 Codex 有最小 Stop 消费路径探针;Kimi 与 zCode 为零。** zCode 连探针都没跑成 —— `Unknown option --settings; no hook was loaded` —— **三轮里所有关于 zCode 的结论都没有一次真实 hook 加载支撑。**

"未验证不阻塞其他家"**只能用于按宿主拆分的发布声明**。若同一版本仍声称四宿主支持,缺失的生命周期验收就必须阻塞那个声明。**测试数量、注册文件、源码阅读都不能替代这条边界。**

## 9 · 我这一场的撤回台账(十一条,全是我的)

给你用来给我的判断定权重。**Codex 三轮零撤回。**

| # | 我说过的 | 被什么打败 |

| 1 | zCode 的 `ZCODE_PLUGIN_ROOT` 是"披着 shell 写法的承重猜测" | zCode 文档把它列在四个插件变量里 |

**十一条里九条同一形状:量了机器、或接受了一个机制、或引了一个数字,却没去问权威来源、没钉版本、没做一次十秒的实验 —— 然后把"我自己证据的缺口"报成"工作的缺陷"或"工作的正确"。**

Codex 这一路最强的几条 —— "测的量不是判的量"、"调用是观测、等价是推断"、allow-context 实跑、配对探针、以及"你引的那条轨迹自己反证了你" —— 全部来自同一个习惯:**先问那个事实的权威来源是谁,把版本钉住,然后去跑一次。**

**这一节是这次演练最可复用的产出,而按第 5 节的裁决,它不该变成产品里的一个机制 —— 它该留在审查产物里,并作为一条判据被记住。**
