# Ultra Goal 综合方案

2026-09-04。作者:Claude Code(Opus 5)。这份是把两条独立路线合成一个可执行方案:

- **我这一路**:三轮 zCode 实现 + 我与 Codex 对抗审查,产出 `host-adaptation @ 073a801`(v2.9.2,358 测试),以及原生目标模式实现挖掘与 Protoss 真实循环对照。记录在 `docs/wip/reviews/`、`docs/wip/protoss-comparison.md`。
- **Codex 那一路**:三家各三轮对抗 + 已安装 CLI 上的真实探针,产出 `方案与论证.md` / `裁决与验证.md` / `evidence.json`。

**合成的结果不是取中点。它那一路在"四家宿主到底会怎么做"上赢了,因为它跑了真探针;我这一路在"目标文档如何进化"上有它没有的东西。而它推翻了我方案里三处,其中一处是我亲手引入并写进提交信息的活缺陷。**

## 0 · 一句话架构

采纳 Codex 的框法,它比我原来的准:

> **主模型持有目标与反馈,脚本记录可核对事实,hook 补漏,宿主提供执行与续跑。**

我原来的说法是"门就是循环,所以不需要宿主的目标模式"。**这句过强。** 推翻它的读数来自 Codex 的第 145 条:Kimi 第一轮跑了约 56 分钟、原生 trace 记录 134 次工具调用、**一次 `CreateGoal` 都没有**。也就是说**普通宿主回合本身就能长时间执行多步任务**;没保证的只是"结束后自动开下一轮"和"进程死后复活"。

Stop 只承担一个很窄的职责。它不是调度器,不是全过程验证,不是无限续跑。

## 1 · 必须先修的四条(分支今天带着,我三轮审查全部放过)

这四条决定了 `host-adaptation` **不能按现状合并**。前三条有实跑证据。

### 1.1 CC 上 allow 附带 `additionalContext` 会续跑

`evidence.json` 探针 `clean-claude-allow-context`,干净 settings、隔离目录、2.1.260:hook 只发
`hookSpecificOutput.additionalContext` 不带 `decision`,而 `hook_events` 出现 index 1 与 2,
`visible_responses: ["PROBE_CORRECTED"]` —— **回合没结束,模型还照注入内容动了。**

这打在我设计的核心规则上。`goal_stop._allow(reason, context)` 有五条路径挂 `additionalContext`:
ceiling 到、unknown、green、空转、预算用尽。**它们在主力宿主上不是"结束并告知",是"一边说
停下一边不让停"。**

**修法:放行不附带模型上下文。** 义务改由两处承载 —— 一是**阻塞时**的 reason(唯一确定会
送达且确实结束不了的通道),二是下一次可注入事件(`UserPromptSubmit` / `SessionStart`)。

**这条同时废掉一条业主规则的实现方式,不废掉规则本身。**"提醒你什么就是你能改什么"仍然
成立,但它的投递通道被证伪了:放行不能带话。

### 1.2 `python3 X || python X` 启动器吞掉 exit 2

我 v2.7.0 为 Windows 兼容写的。Codex 指出它在隔离复现里跑了两次,我自己复现确认:

```
$ echo '{"x":1}' | python3 probe.py                       → RAN stdin=8, exit=2
$ echo '{"x":1}' | sh -c 'python3 probe.py || python probe.py'
  RAN stdin=8      ← 第一次,故意 exit 2
  RAN stdin=0      ← 第二次,stdin 已被吃光
  最终 exit=0      ← exit 2 被吞
```

当时我的理由是"后半只在命令找不到时触发,因为这些 hook 真跑起来一律退出 0"。
**exit 2 恰好就是四家文档里"有意纠正"的机制。** 这个理由十秒钟可测,我却直接写进了提交信息。

**修法:先选解释器,再只执行一次,保留退出码。**

### 1.3 exit 2 的保护必须覆盖启动路径

Codex 第三轮实测:**Python 文件不存在、argparse 参数错误,都返回 2。** 而四家都把 2 当作
"有意阻塞"。我们的 fail-open 全活在 `run_hook` 的 `try/except` 里 —— **进不到那里的失败,
会被宿主读成一次阻塞。**

**修法:启动路径与参数处理也要有保护,不能只靠脚本内部。**

### 1.4 `.goals/active` 没有会话归属

只按 cwd + slug 指向目标。**同一个 cwd 里另一个任务的 Stop 也会触发我们的检查。** 三轮审查
没人提过。

**修法:active 记录当前会话 ID;Stop 只认领会话匹配的 run。** 并且照 Codex 的限定:真实
session ID 是**归属信息,不是防伪密钥**。

### 附:Codex 上 deny 可能整个失效

探针 `clean-codex-invalid-json`:含 `hookSpecificOutput` 的 Stop 载荷,只有一次 hook 事件、
只有 `PROBE_INITIAL` —— **没有产生纠正。** 而我们的 `_deny` 同时发两种形式。

我第 1 轮把"两个权威源都发"记成优点(说它"在一个和两个权威源都无关的宿主上回本了")。
**在 Codex 上它可能是让阻塞整个失效。** 这条我列为"需要一次针对性探针确认",因为现有探针
测的是非法组合,不是我们确切的载荷形状。

## 2 · 一条我读错的量(它连带影响我第 2、3 轮的整个机制)

我从 2.1.260 二进制读出 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP ?? 8`,据此设了"每家预算 = 上限 − 1"。
Codex 指出上限是"**连续无工具进展**的续跑保护,工具使用会重置计数"。我回去核了:

```
stopHookBlockingCount: 0      ← 在状态转移里被重置
go > 0 && blockingErrors.length === 0 → 记 count: go
blockingErrors.length > 0 → qd = go + 1;  if (qd > Vd) 强制结束
```

`go` 就是 `stopHookBlockingCount`。**它数的是"距上一次进展以来的连续阻塞",不是"每回合的
阻塞数"。我读对了数字,读错了那个量。**

后果分两半,要分开说:

- **方向是安全的。** 我们的 `_block_streak` 按回合身份划界并提前一格释放,所以永远早于宿主
  的强制结束。这一半不需要改。
- **理由是错的。** "预算 = 宿主上限 − 1,宿主上限只是兜底"这个说法不成立,因为两边数的不是
  同一个量。真实进展会让宿主归零而我们不归零。

**修法:保留机制,重写它的依据,并把"我们数的是什么、宿主数的是什么"写在同一处。**
这正是我第 2 轮被 Codex F2 指出的那个错误(测的量不是判的量)——**它在更高一层又出现了一次,
而我三轮里两次重新推导都没看见。**

## 3 · Anchor 放在哪:两份文档都没给出的第三种答案

这是我唯一超出两份文档的主张,所以单独标出来。

**Codex 主张**:验证放在普通工具调用里,完整测试不应在每次 Stop 中重跑。
**我原本主张**:Stop 每轮跑 anchor,退出码即裁决 —— 这是 UltraGoal 相对原生模式唯一的实质
优势(原生评判器只读 transcript,失败措辞是 `"insufficient evidence in transcript"`)。

两条都对一半。**分层:**

| 时机 | 谁跑 anchor | 为什么 |
|---|---|---|
| 每次业务迭代 | **运行,当作普通工具调用** | 输出进 transcript,模型能读能反应;这是反馈该在的地方 |
| 运行声明完成时 | **门跑,一次** | 这是"退出码打败自述"唯一真正要紧的时刻 |
| 其他每次 Stop | **不跑** | 只检查"本状态下必需的证据在不在" |

这样保住了机械裁决(在它唯一重要的时刻),去掉了每轮 540 秒的成本,也消掉了"超时=unknown"
在每轮都可能发生的噪声。

**需要一个可核对的锚点:** 运行跑 anchor 时把退出码与输出摘要写成事件;门在完成声明时比对
"这条证据是否对应当前工作树状态"。**标识匹配只说明对应关系,不说明内容正确** —— 这是 Codex
的限定,照抄。

## 4 · 解冻(两份收敛,它补上我漏的一半)

我的主张:**冻结条件,不冻结文档。** 依据是原生目标模式的实现 —— 不可变的是那一句条件
(在会话状态里,模型碰不到),文档完全可变,提示词只是指着它。所以 Protoss 的 `GOAL.md`
被改 38 次没有违反任何东西。

我们把两者混成一件:把条件写进了文档,于是只能去冻结文档。而**代码本来就没禁止** ——
冻结节变动那一步走的是 `_allow`,只报告。**禁止只活在四处提示词里。**

Codex 第 50 条独立收敛到同一处,并补上我漏掉的一半:

> 合法修改目标后**建立新证据基线,保留旧观察**,不能让第一次 frozen digest 永远阻止新约定。

**合并后的改动(删除形状,代码不动):**

| 位置 | 现在说 | 改成 |
|---|---|---|
| SKILL.md 门表 | frozen, challenge don't edit | 改了要留痕:一条轨迹 + 一个裁定 ID |
| 模板 `## Boundary` | 三条拒绝不可改 | 拒绝仍是拒绝;改动记录在 decisions |
| SessionStart 前言 | frozen for the duration | 这是本轮的条款;要改先记 |
| Stop 义务段 | 写挑战而不要编辑 | 挑战是一条路,改并留痕是另一条 |
| digest 措辞 | "已不是业主授权的目标,停下" | "第 N 轮 spec 动了,这是 diff,记下裁定,**并建立新基线**" |

**加一个第四种结果 `impossible`** —— 此会话内不可能达成。判据照抄原生模式:

> the assistant claiming the goal is impossible is evidence, not proof; independently confirm

Codex 提到 CC 评判器有"未满足/满足/不可能"三态但没提议采纳;我主张采纳,因为我们现在
green / red / unknown 里,**"永远达不到"被折进了 red,而这两者的正确反应完全不同。**

## 5 · 进化四件(我这一路独有,来自 Protoss 对照)

`~/projrect-Protoss`:391 提交,`docs/wip/loop-engineering/` 14,561 行,由 CC 原生目标模式
驱动,代由 git worktree 承载。354/391 提交是 tick,标题不是"做了什么"是"我错在哪"。
Codex 那份没有涉及这个对照。

1. **轨迹与状态分家。** 新增 `<slug>.trajectory.md`,append-only,一 tick 一条,四要素:
   sha、谁、**为什么**、证据在哪 —— 外加**当时不知道什么**。`### Lessons` 保持修剪 3 条。
   > TRAJECTORY 原文:*凡是判断,写下当时的理由与当时不知道的东西 —— 事后回看时,当时不
   > 知道什么比当时做了什么更有信息量。*

   复现过的失败:我们那 3 条上限不是预算,是失忆装置。Protoss 自己的日志抓到过这条 ——
   *today's most repeated lesson lived only in the log, not the protocol*。

2. **裁定有 ID、有作者、能覆盖。** 更正用划线 + 指向新行,不删除
   (`~~按裁定 P…~~ ⚠️ 已由裁定 S 更正为四项`)。而 `## Carry-over` 的"删掉不再为真的"必须
   **排除 decisions** —— 否则我们的规则会把更正连同错误一起删掉。

3. **撤回台账 `## Retractions`。** 任何一方撤回过的主张,连打败它的证据一起留。
   复现过的失败:这一场我撤回**六条**(见第 8 节),全是我的;除了散文没有任何地方记着。

4. **校验承诺,不只校验形状。** `--audit` 增加"每个 `goal(<slug>) turn N` 提交是否有轨迹
   条目",join 改成**按标题写入、下一阶段回填 sha**(提交装不下自己的 sha)。
   > Protoss 那个脚本的注释:*A promise that is not checked is not a contract.*

**不抄的:** 1084 行 GOAL.md、七步固定流程、两套裁定编号、按 vendor 派 slot 的调度。那些是
巨型项目的定制装置。**但"scope 完全不相交"作为唯一允许并行写入的条件是对的。**

## 6 · 停做的

- **不再每次 Stop 跑完整 anchor**(见第 3 节)。
- **不再把"两次相同签名即放行"当硬规则。** Codex 第 22 条:相同失败输出或文件树没变化,
  不能证明没有进展;**两次失败便退出会误伤调查和长期修复。** 我一直把它标成"可挑战"却
  从没解决,它解决了。改成:记录 + 提示,不自动释放。
- **不把 `FROZEN_SECTIONS` 做成制品声明。** 能改的是 `ceiling:`、`budget:` 这类阈值;
  **不能改的是"哪些东西算冻结"** —— 一旦制品声明它,运行就能改那行声明来解冻。
- **不读未文档化的字段,哪怕它就在那儿。** Kimi 传 `stopHookActive` 而它按构造恒为 false。
- **不再为省 anchor 时间加"工作树有没有变"的判断。** 第 3 节的分层已经解决了成本问题。
- **不宣称四家已验证。** 见下节。

## 7 · 验收:每家一份清单(采纳 Codex 第 127 条,它比我的完整)

**当前实机覆盖率:CC 与 Codex 有最小 Stop 消费路径探针;Kimi 与 zCode 为零。**
其中 zCode 连探针都没跑成:`Unknown option --settings; no hook was loaded` ——
**三轮里所有关于 zCode 的结论都没有一次真实 hook 加载支撑。**

每家至少验:

1. 激活后确实收到 hook
2. 故意漏一次必要步骤,能够纠正
3. 真正放行能够结束(**这一条 CC 上今天是失败的,见 1.1**)
4. 错误/超时不记成功
5. 同 cwd 的另一个 session 保持无影响(**这一条今天做不到,见 1.4**)
6. 取消与压缩/恢复遵守真实生命周期
7. 必要 worker 结果收齐后才形成结论
8. 原生 goal 已停而 Ultra 证据不足时如实报告

**没有实际跑过的表面标为未验证。** 不用测试数暗示覆盖:358 条测试量的是这个仓库的逻辑和
打包约定,不是"宿主认这个注册"。

## 10 · 交给 Codex 的三个问题

这份文档要请 Codex 逐条攻。特别是这三处,因为它们是我在它证据之上做的**新主张**,没有
第二个人验过:

1. **第 3 节的 anchor 分层** —— "运行每轮跑、门在完成声明时跑一次"。它主张验证全放普通工具
   调用;我认为完成声明那一刻必须有机械裁决。**这个分层是否引入了新的自述缺口?**
2. **第 4 节的 `impossible` 第四态** —— 值不值得加,还是"永远达不到"折进 red 也够用?
3. **第 5 节的四件进化机制** —— 它整份文档没涉及 Protoss 对照。**这四件里有几件其实是
   "没有复现过的失败就加机制"?** 我认为轨迹与撤回台账各有一次(3 条上限截断认知史;
   我这一场六条撤回无处可记),另两件我承认更弱。

另外请它确认或推翻一条:**我们确切的 `_deny` 载荷形状在 Codex 上是否真的失效**
(现有探针测的是非法组合,不是我们的形状)。
