# Codex 独立审查：第一轮

## 产品判断
Ultra Goal 应当把目标澄清、证据约定、执行判断、反馈与恢复组织成可移植的技能。持续唤起模型的能力属于宿主；不能把 Stop 回调描述为四家共有的无限续跑引擎。当前实现有可复用基础：目标文档、明确作用范围、验证命令、Carry-over、结构化事件和独立审查。但“Stop 就是 loop”与代码及宿主限制不符。

## 独立复核的事实
1. main b07e2a8 的 goal_hooks.py 在 stop_hook_active 为真时无条件 return 0。隔离子进程复现：首次失败返回 block，重入没有输出，也没有新验证记录。
2. active_goal 只按 cwd + .goals/active 识别执行目标，没有 session 绑定。隔离复现：相同目录的另一个 session 也执行验证并写入事件。
3. main goal_stop.py 的绿色分支允许存在未勾选 Acceptance，并明确说不等于目标完成。它返回 additionalContext；在不同宿主上，这不是同一种行为。
4. CC 现行官方 hooks 文档：Stop 的 additionalContext 会继续对话，适用连续续跑保护；因此 _allow(reason, context) 不是 CC 上的真正放行。Codex 本地源码 hooks/src/events/stop.rs 聚合时只有有效 block 才保留 continuation_fragments；Kimi triggerBlock 的允许路径不提供 Stop 反馈注入。
5. Kimi 0.40.1 turn/index.ts 942-970：外部 Stop 每个普通回合最多续一次；driveGoal 的外层循环是独立机制。CC 默认 8 次连续无进展保护，工具进展会重置计数；zCode 文档为最多连续 3 次。Codex 检查的源码未见固定次数上限，但不代表任意未来版本保证无上限。
6. Codex hooks discovery.rs 634-653：prompt / agent hook 配置变体存在，但加载时明确跳过 unsupported；不能把 CC prompt hook 当成跨宿主共同能力。
7. main 测试 69 项通过；adapt f15a003 的同一测试文件 93 项通过。它们证明 Python 发出预期数据，不证明宿主按预期续跑/放行。见 local-evidence/verification.md。

## 当前协议过重或过窄的地方（判断）
- 无论任务大小固定设计评审、reviewer、critic；每阶段都问用户选谁，可能违背自发、灵活、低打断目标。需要保留按任务风险选择审查的权利，以及用户已经指定的方式。
- 每轮必须 test-first、必须 Git commit，以及拒绝任何 task ledger/plan，都是超出“目标与证据”所需的限制。当前用户并未授权自动提交。动态待办不必变成预先固定路由。
- 全部场景强制单条 shell anchor，会把研究或语义结果伪装成可由 exit 0 判定。可以有机械验证，但完成证据应按具体验收项约定；不能用脚本替代语义判断。
- 两次相同日志摘要不足以证明停滞，日志变化也不足以证明进展。
- Stop 内运行完整验收，默认最多数分钟，可能阻塞收尾，且错过获得证据以后由模型解释和更新状态的时机。更稳的默认是执行回合内完成验证与记录；Stop 做短而确定的遗漏检查，必要时只给一次补救反馈。

## 尚未定案，交给交叉质询
A. 可否明确优先使用各家原生 goal 负责跨回合续跑，Ultra 自己负责目标和证据？组合时谁控制暂停与完成，双循环是否冲突？各家是否存在技能可实际调用的创建/暂停路径？

C. 完成证据如何绑定目标修订与产物版本而不过度生成状态文件？最低可以只扩展现有 goal.md / events.jsonl，而不增加数据库或调度器。
D. Stop 出错应允许宿主结束，但保持“结果未知”；如何让当前回合看到未知，而不是依赖下一次用户输入？
E. 用户暂停不必触发 Stop，权限拒绝也不是 Stop 可兜底的事件。如何利用已有宿主权限与中断路径，并让恢复文件仅表示事实，不产生继续执行的授权？

## Provisional smaller alternative to attack
- One existing host model owns the live work loop. The skill tells it how to clarify intent, investigate consequential uncertainties, select a next useful slice, delegate when worthwhile, inspect results, verify, update the existing goal/decision files, and continue ordinary tool work. These logical iterations need not end a host turn.
- Native goal mode, when available and actually armed through exposed host operations, owns cross-turn continuation and host accounting. Plain skill mode remains explicitly bounded by the host; a skill does not promise process-death resurrection or unlimited unattended operation.
- Verification happens explicitly during normal work. Scripts can capture exact commands, exit status, affected artifact/goal revision and result paths. Semantic review is selected when required by the task or cost of error. An emitter cannot create semantic certainty by hashing its own statements.
- Stop is an event-limited omission/correction backstop. It performs only short deterministic checks on the current run, may request a bounded correction when an authorized useful action is available, and releases on user control, host limits, known waits or failures without declaring the goal complete. It does not launch a new orchestration loop or run every expensive acceptance test on every stop.
- Recovery uses the actual supported injection events and pointers to state already written. Session/run ownership prevents another session or worker from arming the coordinator. Missing context/source/session identity disables enforcement rather than falling back to an unrelated cwd. In-flight work and unknown results remain explicit.
- Reuse goal.md (contract + current state), decisions.md (meaningful decisions/changes) and relevant evidence/worker result paths. Keep evidence supporting accepted conclusions; do not force a new graph/state database, hash-chain ledger, research file, or Git commit per iteration.

This is a candidate, not a conclusion. If a simpler or stronger arrangement survives these objections, propose it. In particular decide whether bounded Stop correction adds enough value over a purely observational Stop, and whether generic checkpoint checks are real invariants or speculative ceremony.

# 会话归属

# Session ownership binding: source evidence

The session ID is a correlation value visible to the model, not a secret or anti-forgery key. Its legitimate use is preventing accidental activation in another session or worker sharing the same directory.

- Codex: hook_runtime.rs sends sess.session_id().into() as hook session_id. session/session.rs:589 returns SessionId, while exec_env.rs:39 injects that identity as CODEX_SESSION_ID. CODEX_THREAD_ID is a different identifier; do not substitute it merely because StopRequest uses a legacy ThreadId-shaped field. Native thread-spawn children are routed to SubagentStart / SubagentStop, and tool hooks carry subagent context. Bind CODEX_SESSION_ID for the root hook path, keep root vs subagent event/provenance filtering, and verify that the actual arm value equals a real hook payload. Shell snapshots preserve current runtime identifiers (tools/runtimes/mod.rs).
- Claude Code 2.1.260 installed bundle: skill content expansion includes `bn.replace(/\$\{CLAUDE_SESSION_ID\}/g,K())`. Thus a skill invocation can pass its expanded session identity to an explicit arm helper. This does not imply it is a secret.
- Kimi 0.40.1 installed bundle: skill expansion does `content.replaceAll("${KIMI_SKILL_DIR}", context.skillDir).replaceAll("${KIMI_SESSION_ID}", context.sessionId ?? "")`. Missing identity yields empty text and should not silently fall back to cwd ownership.
- zCode 0.16.5 installed bundle: u0t / pV prepare ZCODE_SESSION_ID and CLAUDE_SESSION_ID from the runtime sessionId for command/skill expansion. Outside runtime session context, the resolver explicitly throws `Plugin variable requires a runtime session context` for these variables.

A small arm command can bind the selected goal/run to a host-provided identity. Do not use first-hook-wins, newest-log-wins, or cwd alone. Validate the binding against later hook payloads. These are source observations; the complete arm-to-hook path on each host still requires lifecycle smoke testing before claiming verified support.

# 启动器的退出码

# Launcher swallows intentional Stop exit 2

The pinned main/adapt command hooks use interpreter fallback of the form python3 script || python script. A shared exit-2 Stop protocol requires changing that launcher: exit 2 means an intentional control effect, not a missing interpreter. An isolated shell reproduction with both interpreter aliases present invokes the hook twice; the second invocation has empty stdin and exits 0, so the host sees allow. If the fallback interpreter is absent, the final non-2 shell error also loses the intended block.

Observed result: exit 0; two calls; first stdin nonempty, second stdin empty. See launcher-probe/result.json. This is a launcher experiment, not another live host lifecycle run.

Minimum correction: choose an available interpreter BEFORE executing the hook, then propagate that one invocation's exit status. Reuse installer-resolved interpreter/host argv support where available. Do not treat an arbitrary nonzero hook exit as a reason to invoke it again. Also normalize accidental argparse/usage exit 2 separately from an intentional Stop correction.
